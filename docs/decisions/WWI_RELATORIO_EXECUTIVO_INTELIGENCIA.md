## 3. Por que motor de regras em vez de LLM (justificativa completa)

1. Não existe hoje, em nenhum lugar do código (`app.js`, `index.html`, `.github/workflows/*`, `scripts/sync/*.py`), nenhuma integração com API de LLM (OpenAI/Anthropic/etc) em produção — adicionar essa dependência sem pedido explícito abriria uma chave de API nova, custo recorrente e uma superfície de falha de rede numa feature que deveria ser "gerar um PDF a partir de dado já calculado".
2. Um LLM real geraria texto não-determinístico sobre dado financeiro pessoal sensível — risco real de alucinar um número que não bate com o card real, exatamente o tipo de bug que este projeto trata como inaceitável (ver comentário de `coletar-dados-relatorio.js`: "fonte única... nunca pode dessincronizar").
3. O padrão dominante do projeto inteiro é "ler o que já foi calculado, nunca reimplementar/reinterpretar por conta própria" — um motor de templates que monta frases a partir de comparações determinísticas é a extensão natural desse padrão, não uma ruptura.
4. Se no futuro for desejado um LLM real (variar tom da narrativa, resumir texto livre), isso vira uma Fase 2 opcional isolada — o motor de regras continua como base/fallback, e qualquer texto gerado por LLM ainda seria ancorado nos mesmos números (o LLM reescreveria estilo, nunca inventaria valor).

## 8. Correção da divergência JS×Python — Caixa Lance no Patrimônio Líquido do WWI (14/08/2026)

**Achado de auditoria**: os dois motores (`src/relatorio/gerar-analise-financeira.js`, roda no navegador lendo o DOM do painel; `scripts/sync/wwi_gerar_relatorio_mensal.py`, roda via job mensal lendo SQL direto) divergiam em exatamente **R$2.630,26** em `patrimonioFinanceiro`/`ativosTotal`/`patrimonioLiquido` — coincidência exata com o saldo real da Caixa Lance (`vw_saldo_v2_por_caixa`, confirmado nesta sessão via SQL).

**Causa raiz**: o lado JS lê esses 3 campos direto do DOM do painel (seções "🏦 Balanço Patrimonial" e "🏛️ Patrimônio Financeiro"), que por sua vez vêm de `REG.patrimonio.total`/`REG.balanco.*`, calculados por `recalcularPatrimonio()` (`src/financeiro/patrimonio/recalcular-patrimonio.js:31`, `bfin.total = reserva+btg+necton+consorcioCasaPago`) — fórmula que **exclui Caixa Lance por design**. Essa exclusão está correta no contexto onde é usada (Painel Executivo, Balanço — já auditada antes) mas o job Python **sempre incluiu** Caixa Lance (`patrimonio_financeiro = financeiro_sem_lance + caixa_lance`, `vw_patrimonio_v2.patrimonio_financeiro_liquido_sem_lance` + soma manual).

**Decisão explícita do usuário**: Caixa Lance deve entrar no Patrimônio Líquido do WWI — **só do WWI**. `recalcularPatrimonio()`/`REG.patrimonio.total` não foram tocados (continuam sem Caixa Lance para Painel Executivo/Balanço, que é o comportamento correto lá).

**Correção aplicada (só no lado JS — o Python já estava certo)**:
- `src/relatorio/gerar-analise-financeira.js`: `calcularIndicadoresEScores(dados, caixaLanceSaldo)` ganhou um 2º parâmetro opcional — quando presente, soma `caixaLanceSaldo` a `patrimonioFinanceiro`/`ativosTotal`/`patrimonioLiquido` logo depois de extraí-los do DOM (só quando o valor de origem já existe — nunca fabrica um total que o coletor não achou). `gerarAnaliseFinanceira(dados, caixaLanceSaldo)` repassa o mesmo parâmetro. Nova função `wwiBuscarSaldoCaixaLance()` busca o saldo via `WallaceFinanceService.getSaldosPorCaixa()` (mesmo caminho cacheado já usado por `hydrate-onda3-caixalance.js` — nenhuma chamada Supabase nova).
- `index.html` (`gerarRelatorioFechamentoPDF()`): agora busca `caixaLanceSaldo` (via `win.wwiBuscarSaldoCaixaLance()`) **antes** de chamar `calcularIndicadoresEScores()`/`gerarAnaliseFinanceira()`, e passa o valor pros dois.
- `scripts/sync/wwi_gerar_relatorio_mensal.py`: **nenhuma mudança** — já estava correto (confirmado por leitura + pelos números validados abaixo).

**Validação numérica (SQL direto, 14/08/2026, Nível A)**:
- `vw_saldo_v2_por_caixa` → Caixa Lance = R$2.630,26 (bate exatamente com a divergência apontada pela auditoria).
- `vw_patrimonio_v2` → `patrimonio_financeiro_liquido_sem_lance=115.209,37`, `fisico_total=430.800,00`, `consorcio_casa_pago=2.898,90`, passivos = 61.081,39+18.998,83 = 80.080,22.
- Python: `patrimonioFinanceiro = 115.209,37+2.630,26 = 117.839,63`; `ativosTotal = 117.839,63+430.800,00+2.898,90 = 551.538,53`; `patrimonioLiquido = 551.538,53−80.080,22 = 471.458,31`.
- JS (fórmula do DOM, calculado à mão): `bfin.total (patrimonioFinanceiro sem Lance) = 100.000+14.779,62+429,75+2.898,90 = 118.108,27`; `ativosTotal sem Lance = 430.800,00+118.108,27 = 548.908,27`; `patrimonioLiquido sem Lance = 548.908,27−80.080,22 = 468.828,05`. Somando Caixa Lance (2.630,26) aos 3 campos: `ativosTotal = 551.538,53`, `patrimonioLiquido = 471.458,31` — **idêntico ao Python**, e ao valor já documentado/validado no Test Run real (seção "Status" no topo deste arquivo).

**Diferença de fórmula encontrada além da Caixa Lance (documentada, não corrigida — fora do pedido explícito do usuário)**: o `patrimonioFinanceiro` intermediário dos dois lados **não tem a mesma composição**, mesmo depois desta correção — só os totais finais (`ativosTotal`/`patrimonioLiquido`) batem. O JS inclui `consorcioCasaPago` dentro de `bfin.total` (linha 31 de `recalcular-patrimonio.js`: `reserva+btg+necton+consorcioCasaPago`), enquanto o Python mantém `patrimonio_financeiro_liquido_sem_lance` **sem** o consórcio e soma `consorcio_casa_pago` separadamente só na hora de montar `ativos_total`. Isso não afeta `ativosTotal`/`patrimonioLiquido` (a soma total é igual dos dois lados), mas afeta o **sub-score "investimentos"** (`patrimonioFinanceiro / patrimonioLiquido`), que usa `patrimonioFinanceiro` como numerador — o JS conta R$2.898,90 a mais nesse numerador que o Python, para o mesmo ciclo. Não corrigido nesta sessão (fora do escopo pedido — só Caixa Lance foi objeto de decisão explícita); registrado aqui para o usuário decidir se quer unificar também essa composição no futuro.

## 8. Incidente 14/08/2026 — linha de `historico_relatorios` apagada sem rastro, causa raiz e correção (Nível A, confirmado por SQL)

**Sintoma reportado**: `historico_relatorios` com 0 linhas, mas `vw_saude_jobs` mostrando `wwi_relatorio_mensal` com `ultimo_status='sucesso'` (última execução `2026-08-14 14:13:31 UTC`) e este documento descrevendo uma linha real gravada e corrigida pra `2026-07`.

**Investigação (evidência real, não suposição):**
- `edge_logs` confirma **um único** `POST /rest/v1/rpc/wwi_upsert_relatorio_mensal` às `2026-08-14 14:13:30 UTC`, de `Python-urllib/3.11` — é o job real rodando, batendo com o heartbeat. `wwi_upsert_relatorio_mensal()` (`pg_get_functiondef`) faz um `INSERT ... ON CONFLICT DO UPDATE ... RETURNING ... INTO v_resultado` de verdade — se o `INSERT` falhasse, a função levantaria exceção e o script Python trataria como erro (`except Exception`, heartbeat viraria `erro`). **Não é bug de "sucesso do processo ≠ sucesso da gravação"** — a gravação real aconteceu.
- A correção do bug de `consorcio_casa_pago_pct` (commit `0886352`, seção 7 acima) também é real: `pg_stat_statements` tem a query exata `select wwi_upsert_relatorio_mensal($1,$2,$3::jsonb,(select analise_ia from historico_relatorios where competencia=$4))` com `rows=1` — a linha existiu, corrigida, confirmada.
- **Causa raiz da perda**: `pg_stat_statements` mostra `delete from historico_relatorios where competencia = $1` com `calls=2, rows=2` — ou seja, em toda a história da tabela houve exatamente 2 `DELETE`s, cada um removendo 1 linha, cada um **corretamente filtrado por competência** (não um `DELETE` genérico sem `WHERE` nem filtro errado). Um deles é o cleanup documentado da linha de teste `'9999-99'` da Fase B (seção 6). O outro **não está documentado em lugar nenhum** e removeu a linha real `'2026-07'` depois da correção do bug — não foi possível identificar quem/quando exatamente rodou esse segundo `DELETE`: nem `postgres_logs` (roda com `log_statement=ddl`, só grava DDL, nunca DML, mesmo via conexão direta) nem `edge_logs` (só captura tráfego via PostgREST/REST — o `DELETE` não passou por lá, foi SQL direto numa sessão com acesso ao banco) guardam o texto/autor do comando. Essa é uma limitação real, não contornável agora — o rastro não existe porque nunca foi capturado, não porque foi apagado depois.
- **Por que ninguém viu isso passar**: `historico_relatorios` nunca teve trigger de auditoria (confirmado via `information_schema.triggers` — só `caixas`, `transacoes`, `indicadores` tinham `trg_audit_*`). Mesmo que o `DELETE` tivesse passado pela API REST, nada teria ido para `audit_log`.

**Correção aplicada (`apply_migration`, 2 migrations):**
1. `trg_audit_historico_relatorios` — trigger `AFTER INSERT OR DELETE OR UPDATE` ligado a uma função nova, `fn_audit_log_historico_relatorios()`. **Não reaproveita** `fn_audit_log_generic()` (a mesma das outras 3 tabelas) porque essa assume uma PK `uuid` chamada `id` — `historico_relatorios` tem PK `competencia` (`text`); reaproveitar cegamente teria quebrado todo `INSERT`/`UPDATE`/`DELETE` na tabela (confirmado batendo o erro real: `record has no field id` na primeira tentativa). A função nova grava em `audit_log` normalmente, com `registro_id` = `md5('historico_relatorios:' || competencia)::uuid` (determinístico, mesma competência sempre mapeia pro mesmo id — só descoberto depois de bater outro erro real, `audit_log.registro_id` é `NOT NULL`, não dava pra deixar `null`).
2. `get_advisors(security)` apontou na sequência que a função nova ficou exposta em `/rest/v1/rpc/fn_audit_log_historico_relatorios` pra `anon`/`authenticated` (todo função `public` é exposta por padrão) — `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated` aplicado (mesma régua de `fn_audit_log_generic`, que só tem `EXECUTE` pra `postgres`/`service_role`). Trigger continua funcionando normalmente depois do revoke (testado com um `UPDATE` real, `audit_log` recebeu a segunda linha).

**Recuperação do dado**: recalculados os indicadores **agora, via SQL direto** nas mesmas views que o job usa (`vw_patrimonio_v2`, `vw_saldo_v2_por_caixa`, `metas`, `reembolso_wartsila_ciclo` filtrada por `ciclo_referencia='2026-07'`) — não copiados cegamente da seção 7 deste documento. Patrimônio líquido recalculado bateu **exatamente** R$ 471.458,31, Wealth Score recalculado bateu **exatamente** 53/100, eficiência de reembolso Wärtsilä bateu **exatamente** 95,4% — os 3 números batendo com o que já estava documentado é a confirmação de Nível A que faltava (fórmula E dado atual convergem, não é coincidência de copiar valor antigo). Linha reinserida via `wwi_upsert_relatorio_mensal('2026-07', ...)` chamada direto por SQL. Campos sem fonte confiável (`totalOperacional`, `liquidez`, `independenciaFinanceira`, `disciplinaFinanceira`, `crescPatrim*`, `poupanca*`) ficaram `null`, mesma limitação já documentada na seção 6 — não fabricados.

## 9.1 Correção de metodologia — `protecaoPatrimonial` duplicava `endividamento` (15/08/2026)

Achado de auditoria de metodologia (analista financeiro sênior): `protecaoPatrimonial` e `endividamento` usavam a fórmula EXATA (`100 - passivos/ativoTotal*100/50*100`), inflando o peso real de "quanto existe de dívida" pra 30% do Wealth Score (15%+15%) sem que isso fosse a intenção documentada dos 7 pesos da seção 4. `protecaoPatrimonial` agora mede debt-to-equity — passivos sobre **patrimônio líquido**, não sobre ativo total: `100 - passivos/patrimonioLiquido*100`, zero quando a dívida iguala o patrimônio líquido. Mais sensível quando o ativo é majoritariamente ilíquido (caso deste usuário — imóvel). `endividamento` continua medindo alavancagem bruta (passivos/ativoTotal), inalterado. Nenhum dado novo — `passivosTotal` e `patrimonioLiquido` já eram calculados nos dois motores, só não eram cruzados dessa forma. Corrigido nos dois lados (`gerar-analise-financeira.js:calcularIndicadoresEScores` e `wwi_gerar_relatorio_mensal.py`), mesma régua de paridade JS×Python da seção 9 abaixo.
